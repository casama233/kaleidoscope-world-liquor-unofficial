# World Liquor 0.1.97 — complete native freezer input stacks

Current maintained authority: NeoForge1.21.1 author1.1.11/CF9066406 `FreezerBlockEntity` owns four `ItemStackHandler` slots and saves their complete NBT. The former Bedrock ID-only implementation rejected names/custom data and reconstructed retrieved/dropped items. World Liquor now owns a private persistent four-slot native entity inventory. The compact machine IDs index the complete stacks; once adopted, missing/wrong-owner/moved/corrupt carriers fail closed and are never replaced with fresh ID-only items. Legacy ID rows remain readable and are adopted on the next mutation, retaining each original plain input. Named/lore/durability/enchantment/dynamic-property/Adventure restriction/keep-on-death data stay inside native cloned stacks rather than a lossy JSON serializer. It requires the existing Tavern host, with no dependency on private cooking integration or luosen-only configuration.

Insertion stores a one-item clone before unconditional held-stack debit, including Creative. Empty-hand removal reads the exact last native slot, preserving differences between identically typed inputs. Milk/output settlement keep their distinct source rules. Crafting consumes/retire inputs only after an owned commit succeeds; SDK faults restore slots, carrier markers and machine state. Lid/permutation failure does not finish the retired carrier prematurely. Whole-stack input drops match `FreezerBlock.onRemove`, including Creative and doTileDrops=false; uncollected output is not a stored input and no fabricated output stack is emitted. The existing block-item drop keeps its separate loot/mode gate. Exact Java dropped-item random coordinates/velocity/hooks remain unimplemented.

Loaded carriers are bounded and pinned only after full ownership/content proof. A moved carrier is rejected on read and queued for controlled recovery; its inventory/identity/state are preserved. Missing carriers never trigger recreation. Player breaking is cancelled on failed proof, and placement retains recoverable existing inputs instead of clearing them. Recovery/error handling is an explicit Bedrock adapter, not equivalence to arbitrary Java hooks, ItemStack reference aliases, crash atomicity or chunk/network phases.

A related API bug is corrected: `isStackableWith` is stacking compatibility, not object identity, and always returns false for intrinsically unstackable items. Ordinary milk buckets/sword inputs therefore cannot use it as a sole captured-origin check. Stackable items still use the engine comparator; intrinsic maxAmount1 copies use stable observable metadata for a read-only guard. Hidden engine/foreign-pack components are preserved by the native stack, but their full captured-origin equality is not exposed by stable APIs and is not claimed. Existing bottle completion shares this guard without changing effect/audio/debit order. Official API references: [ItemStack](https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/itemstack?view=minecraft-bedrock-stable) and [entity inventory](https://learn.microsoft.com/en-us/minecraft/creator/reference/content/entityreference/examples/entitycomponents/minecraftcomponent_inventory?view=minecraft-bedrock-stable).

SDK callback/storage regressions cover distinct same-ID metadata, legacy adoption, exact extraction, failed row write, craft retirement/rollback, owner/content/missing-carrier refusal, controlled reanchor and original removal rules. The native experiment uses real four-slot containers and real named sugar, milk buckets and a sword carrying lore/durability/enchantments/dynamic properties; it checks restart identity/metadata, extraction, rollback, reanchor and retirement without players. Its declared disposable observer overlay is separate from exact family admission. Actual cross-pack private-property ownership and arbitrary-addon/client interaction still need their own observations. Source/SDK checks are not simulated players or rendered-client acceptance.
